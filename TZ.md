## 1. Контекст продукта

- Онлайн-школа подготовки к ЦТ/ЦЭ. Ученики решают задания в Telegram-боте.
- Роли: владелец (owner) → менеджер (manager) → преподаватель (teacher) → ученик (student). Есть гость (guest) — человек, ещё не привязанный к профилю.
- Ученик попадает в бота по **инвайт-коду** (6 символов), который создаёт менеджер. Доступ — по дате окончания подписки.
- Всё время — **Минск, UTC+3** (Беларусь не переводит часы).
- Тон общения бота: коротко, тепло, человечно, с эмодзи. Никакого канцелярита и сухого технократичного языка.

## 4. Схема БД (полная, включая поля-закладки под v2)

Все таблицы создаются в этой миграции. Поля, помеченные `[v2]`, в MVP не используются в интерфейсе, но ОСТАЮТСЯ в схеме.

### users
- `id` PK autoincrement
- `tg_id` bigint, уникальный, nullable (заполняется при привязке)
- `tg_username` string(64) nullable
- `tg_full_name` string(128) nullable
- `role` string(16): owner | teacher | manager | student | guest (CheckConstraint)
- `is_active` bool, default true
- `created_at` datetime(timezone) server_default now()
- `streak_current` int, default 0
- `streak_best` int, default 0
- `last_solved_date` date nullable (UTC+3)
- `last_reaction_id` int nullable (чтобы не повторять две реакции подряд)

### subjects
- `id` PK, `name` string(128), `is_active` bool default true

### teacher_subjects (PK-пара)
- `teacher_id` FK users.id (ondelete CASCADE), `subject_id` FK subjects.id (CASCADE)

### themes
- `id` PK, `subject_id` FK (CASCADE)
- `title` string(200)
- `order` int default 0
- `is_open` bool default false — закрытая тема не видна ученику
- `mode` string(16) default 'sequential', CheckConstraint IN ('sequential','random') — режим «открыть все» `[v2]` (в MVP всегда sequential, но поле остаётся)
- `created_by` FK users.id nullable (SET NULL), `created_at`

### subthemes — `[v2, поле-закладка]`
- `id` PK, `theme_id` FK (CASCADE), `title`, `order`
- В MVP интерфейса подтем НЕТ: задания крепятся прямо на тему. Таблицу оставляем, потому что в v2 вернём.

### tasks
- `id` PK
- `subtheme_id` FK nullable `[v2-закладка]`, `theme_id` FK (CASCADE)
- `question_text` Text nullable, `question_photo_id` string(256) nullable (tg file_id)
- `options` JSON: `[{"t": str, "c": bool}, ...]` — 2–4 варианта, ровно один `c=true`
- `feedback_text` Text nullable, `feedback_photo_id` string(256) nullable — объяснение после ответа
- `order` int default 0, `is_active` bool default true (скрытие задания)
- `created_by` FK nullable, `created_at`

### students
- `id` PK, `user_id` FK users.id (CASCADE), уникальный
- `access_until` date nullable — одна дата на ученика, действует на все предметы
- `invite_code` string(8) nullable, уникальный
- `invite_status` string(16) default 'pending', CheckConstraint IN ('pending','activated')
- `invited_by` FK users.id nullable, `created_at`

### student_subjects (PK-пара)
- `student_id` FK (CASCADE), `subject_id` FK (CASCADE)
- `is_active` bool default true — ручное закрытие предмета менеджером
- `added_at` datetime server_default now()

### attempts (журнал ответов — пишется всегда, экранов нет)
- `id` PK, `student_id` FK (CASCADE), `task_id` FK (CASCADE)
- `answer_index` int nullable, `is_correct` bool
- `answered_at` datetime(timezone) server_default now()
- Индексы: student_id, answered_at

### task_progress (для «осталось N»)
- `student_id` FK + `task_id` FK — составной PK
- `status` string(8) default 'done', CheckConstraint IN ('done','wrong')
- `solved_at` datetime(timezone) server_default now()

### reminder_log — `[v2-закладка]` (таблица остаётся, в MVP не пишется)
- `id` PK, `student_id` FK (CASCADE), `kind` string(24), `reminded_on` date
- UniqueConstraint (student_id, kind, reminded_on)

Правило: в продакшене **нет физических удалений сущностей**, кроме явных случаев (удаление темы/задания преподом). «Кик» = is_active=false.

## 7. Приглашение и привязка (точная логика)

1. Менеджер создаёт ученика → код из 6 символов, алфавит без похожих: `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (без 0/O и 1/I). Уникальность — генерация «до успеха» с проверкой по БД (не более 100 попыток, затем ошибка).
2. Ссылка: `https://t.me/{username_бота}?start={КОД}`. Username бота получаем через `get_me()` и кэшируем (на случай сбоя — фолбэк «LevelUpBot»).
3. Ученик жмёт /start по ссылке или вводит код текстом. Проверки в порядке:
   - кода нет → «Такого кода нет. Проверь у менеджера 🙂»
   - код уже активирован → «Этот код уже использован. Если это твой код — напиши менеджеру.»
   - этот tg_id уже привязан к активному ученику → «Этот Telegram уже привязан к профилю. Если это не ты — напиши менеджеру.»
4. Иначе — подтверждение: «Подтверди, что ты — {имя}?» кнопки «Да, это я» / «Нет, это не я».
5. После подтверждения: `users.tg_id = tg_id`, `invite_status = activated`. Важно: у пользователя, который уже заходил в бота, существует запись с ролью guest и этим tg_id — её нужно удалить перед записью tg_id (иначе нарушение уникальности). Чужие серьёзные роли, занявшие tg_id, — отказ.
6. Приветствие: «Привет, {имя}! 🎉\nТвой доступ: {предметы} — до {дата}. Погнали? 🔥» + меню.
7. «Нет, это не я» → остаёмся гостем, приглашаем написать менеджеру.
8. Повторная попытка с тем же кодом → «Код уже использован».

## 8. Визард «Добавить задание» (точные шаги FSM)

Состояния: `question → options → correct → exp_choice → (exp_text | exp_photo) → preview`.

1. **question**: «Отправь вопрос текстом или фото с текстом:». Принимает текст (≤1000 симв.) или фото (с caption). Оба варианта сохраняют `question_text` и/или `question_photo_id`. После приёма — **обязательно** переход в `options`.
2. **options**: «Присылай варианты по одному сообщением (2–4):» + кнопки «➕ Ещё вариант» / «✅ Готово».
   - Текст (≤200 симв.) → добавляется вариант. Кнопка «➕ Ещё вариант» (и любое добавление) должна **явно устанавливать состояние `options`**, чтобы следующее сообщение попало в нужный хендлер.
   - Максимум 4 → «Уже 4 варианта — это максимум. Нажми «✅ Готово», если достаточно.» (кнопка «Готово»).
   - «✅ Готово»: минимум 2 варианта, иначе алерт «Нужно минимум 2 варианта». Далее — переход в `correct`.
3. **correct**: «Какой вариант правильный?» + варианты кнопками «А. …», «Б. …» и т.д. → сохранение индекса → переход в `exp_choice`.
4. **exp_choice**: «Объяснение ответа — необязательно.\nДобавь текст или фото, или пропусти:» + кнопки «Добавить текст» / «Добавить фото» / «Пропустить».
   - «Добавить текст» → состояние `exp_text`: «Пришли объяснение текстом:». После приёма текста — переход обратно в `exp_choice` (чтобы любое следующее сообщение не потерялось).
   - «Добавить фото» → состояние `exp_photo`: «Пришли фото-объяснение:». После приёма фото — переход обратно в `exp_choice`.
   - В состоянии `exp_text` присылают фото (и наоборот) → короткая подсказка «Пришли текст (или нажми «Пропустить»)» — сообщение не теряется.
   - «Пропустить» → сразу `preview`.
5. **preview**: показ задания как у ученика (фото если есть; вопрос; варианты кнопками — клики по ним отвечают «Это превью — правильный ответ не показывается»). Кнопки: «✅ Сохранить» / «✏️ Заново».
   - «Заново» → состояние `question` с сохранёнными theme_id (без task_id).
   - «Сохранить»: **защита от двойного клика** — сразу убираем клавиатуру у сообщения (edit_reply_markup) и/или помечаем state; при повторном клике отвечаем «Уже сохраняю…». Проверяем наличие `correct` и корректность индекса. Создаём задание, после успеха: «✅ Задание сохранено!» + карточка задания.
6. Любая команда (текст с `/`) во время визарда → отмена визарда и выполнение команды? Нет: **команды во время визарда отменяют визард** с сообщением «Визард отменён» и выполняются. Уточнение: простое правило — текст, начинающийся с `/`, не попадает в хендлеры визарда (фильтр `~F.text.startswith("/")` на всех текстовых шагах).

Примечания:
- Все текстовые шаги визарда — с `@require_role("teacher", "owner")`.
- Переключение состояний — единственное место, где решается, что принимается: текст или фото. После каждого шага состояние обязано смениться (это была критичная ошибка старой версии).

## 9. Флоу решения задания (точная логика)

1. Вход в тему: проверка доступа (раздел 10). Затем:
   - последовательный режим: первое задание без записи в `task_progress` (по order, id). Решённым считается любая запись — done или wrong.
   - скрытые задания (is_active=false) не выдаются.
2. Карточка: «Решено K из M · Осталось L» + вопрос + кнопки вариантов. В callback варианта — seq.
3. Ответ:
   - `attempts` пишется всегда (студент, задание, индекс, правильно/неправильно, время).
   - `task_progress` создаётся только если записи ещё нет (status: done/wrong).
   - Реакция: правильно → случайная из пула позитивных; неправильно → из пула мотивационных. Не повторять два раза подряд: у ученика хранится id последней реакции (`users.last_reaction_id`).
   - Стрик: засчитывается на любой ответ, идемпотентно в рамках дня (первый ответ дня: вчера → +1, сегодня → без изменений, иначе → 1). Рекорд обновляется сразу.
   - Ответ: «{реакция}» + при ошибке «Правильный ответ: А. …» + кнопки «Ещё задание»/«Вернуться к темам». Объяснение — отдельным сообщением(и) после.
4. «Ещё задание» → следующее нерешённое. Все решены → итог:
   - «🏁 Тема пройдена!\n✅ K правильных, ❌ M неправильных» + (если побит рекорд стрика) «И новый рекорд стрика: N дней! 🔥»
   - Кнопки «🔁 Повторить тему» (сброс task_progress этой темы у ученика; attempts остаются) и «📚 Другие темы».
5. Seq-механизм: при выдаче задания в callback кладём `seq` = число попыток ученика по теме на момент выдачи. При ответе сравниваем с текущим числом; не совпало → «Кнопка устарела — возьми задание заново.» + перерисовка текущим состоянием (без падений).

## 10. Доступ и подписка (MVP)

- Ученик = `students.access_until` (одна дата) + `student_subjects.is_active` (ручные переключатели).
- **Единая точка проверки** — функция `can_access(student_id, theme_id)`:
  - ученик существует и активен;
  - предмет существует, активен, назначен ученику и `student_subjects.is_active`;
  - тема существует и `is_open`;
  - `access_until >= today` (по Минску; день окончания — доступен весь день).
- **Правило «текущее досматривает»**: если доступ истёк или тему закрыли ПОСЛЕ выдачи задания — ответ принимается; блокируется только новая выдача. Проверка доступа есть только при выдаче, НЕ при ответе.
- Истёкший доступ при входе: «Доступ истёк. Напиши менеджеру — продлим за минуту».
- Закрытая тема: «Тема закрыта, задания пока не выдаём.» Пустая тема: «Заданий пока нет. Препод скоро добавит 👩🏫».
- Ручное закрытие предмета менеджером → темы предмета исчезают из меню ученика сразу.
- Продление: новая дата, ничего у ученика не меняется.
- Деактивированный пользователь (любой роли) → «Доступ закрыт, обратись к администратору» (обрабатывается в мидлваре, событие дальше не идёт).

## 11. Известные ошибки старой версии — НЕ ПОВТОРИТЬ (критично)

1. **Запуск не из корня**: `env_file=".env"` читался относительно рабочего каталога → пустой BOT_TOKEN → бот падал с 401. Новое: путь к `.env` — абсолютный (`Path(__file__).resolve().parent.parent / ".env"`). Плюс при пустом BOT_TOKEN — понятная ошибка при старте: «BOT_TOKEN не задан. Заполни .env».
2. **delete_webhook на невалидном токене** падал до обработки. Новое: `delete_webhook` — в try/except с логом; `main()` оборачивается в try/except с записью исключения в лог (не только KeyboardInterrupt/SystemExit).
3. **tzdata**: `ZoneInfo("Europe/Minsk")` на уровне импорта без пакета tzdata в requirements → падение на Linux. Новое: tzdata в requirements.txt; ZoneInfo создавать один раз, в одном месте.
4. **Тихие падения БД**: при недоступной базе ошибки возникали в мидлваре, пользователь получал текст без кнопок и без внятной ошибки. Новое: при старте бота — проверка подключения к БД (простой SELECT 1) с понятным сообщением и выходом; ошибки БД в хендлерах — через глобальный обработчик (лог + «Что-то пошло не так, попробуй ещё раз»).
5. **Визард задания замерзал**: шаги объяснения (текст/фото) не переводили FSM, «чужой» тип сообщения терялся молча. Новое: каждое состояние жёстко переводится после приёма (раздел 8); неизвестное сообщение в состоянии — подсказка, а не потеря.
6. **Устаревшие кнопки визарда** (например «➕ Ещё вариант» из старого сообщения) не ставили состояние → следующее сообщение терялось. Новое: каждая кнопка-«ожидаю ввод» явно устанавливает состояние перед ответом.
7. **Мёртвые кнопки**: были callback-данные без обработчиков (например «← Назад» из карточки ученика). Новое: **реестр всех callback-префиксов** (раздел про колбэки в заходе 2): любой callback, созданный клавиатурой, обязан иметь обработчик. Проверяется тестом-реестром.
8. **Двойной клик «Сохранить»** создавал два задания (гонка). Новое: защита из раздела 8 (убрать кнопку сразу + проверка state).
9. **Отсутствие `@require_role`** на текстовых шагах визардов (можно было обойти защиту). Новое: ВСЕ хендлеры, включая текстовые шаги, — с `@require_role`.
10. **Гонка инвайт-кодов**: генерация кода с проверкой уникальности — внутри той же транзакции, что и создание ученика (иначе два параллельных создания могут выдать один код). Код генерируется «до успеха» (цикл) в рамках сессии.
11. **Username бота кэшировался как пустой** после первого сбоя get_me (падала генерация ссылок до перезапуска). Новое: кэш только успешного значения; при сбое — повторная попытка при следующем вызове.
12. **Состояние FSM не чистилось при ошибке в визарде ученика** — следующий визард мог наследовать мусор. Новое: вход в любой визард начинается с `state.clear()`; после успешного завершения — `state.clear()`.

## 14. Технические конвенции (обязательно)

- **Callback-данные:** формат `{entity}:{id}:{action}:{seq}`, seq фиксирован (`0`), кроме задач ученика (там seq = число попыток, раздел 9).
- **FSM-состояния** — в `app/states.py`, по одному StatesGroup на визард.
- **Тексты реакций** — константы в `app/services/reactions.py`.
- **Роли** — `app/utils/roles.py` (декоратор `require_role`).
- **Даты** — всё через `app/utils/dates.py` (Минск, UTC+3).
- **Меню** — инлайн-клавиатуры уровнями, не глубже 3.
- Фото заданий хранятся как tg `file_id` (валидны при том же токене бота; при смене токена — перезаливка, это известный риск).
- README.md проекта обновить под новый код (запуск, тесты, миграции, деплой systemd/Docker).
